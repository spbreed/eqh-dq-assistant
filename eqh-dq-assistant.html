Workflow

  1. Land. 8 health plans, state HIEs and the EHR/CareEmpower drop daily files into the S3 bronze (raw) zone (47 feeds, each with its own quirks).
  2. Catalogue. The Glue Data Catalog registers raw and silver tables and their schemas.
  3. Conform & check. Glue jobs turn raw files into silver Parquet; Glue Data Quality rulesets test them.
  4. Model (gold). Redshift loads core, then builds marts and late-binding views.
  5. Deliver. Payer submissions, practice scorecards, the CareEmpower panel feed and datashares go out.

The target: a governed, read-only data assistant

Find & explain

"Which dataset should I use…", plain-language descriptions, business glossary. AI text is labelled AI draft – not yet approved until a steward approves it.

Trace & impact

Table- and column-level lineage across late-binding views, Spectrum, datashares and extracts. Impact ranked: payer submissions › CareEmpower › practice files › finance › marts.

Watch quality

Daily issues by payer and state: stale feeds, volume drops, nulls, duplicates, orphans, overlaps, invalid values, rule failures, schema drift.

Draft documentation

AI drafts descriptions and flags outdated docs. Stewards approve, edit or reject: the only write path, and it's audited.

Stay safe

Refuses any change to data, schemas or pipelines. Shows metadata and aggregates only, never row data. restricted_bh data is hidden from other users.

Security & governance by design

1

Data residency

  • Every resource in one Region, us-east-1, set in config and never hard-coded
  • Bedrock models, logs and backups stay in-Region
  • Synthetic data only, treated as PHI
2

PII / PHI protection

  • The store, prompts and logs hold metadata and aggregates only, never row values
  • An automated PHI-guard test enforces it
  • KMS encryption at rest; secrets in Secrets Manager
3

AI guardrails

  • Bedrock Guardrail on input and output: a deny topic for any data or schema change, PII anonymisation, and prompt-attack filtering
  • Write-intent check before any tool call
  • Answers come only from tool results, with cited asset keys
4

Agent identity & attribution

  • Users sign in with Cognito; their groups drive entitlements (restricted_bh)
  • The agent runs as its own IAM task role, separate from the users
  • Every answer is logged with user and tools; steward approvals are audited; CloudTrail and Bedrock invocation logs
5

Private networks

  • Aurora, Redshift and the Fargate tasks sit in private subnets
  • VPC endpoints carry AWS traffic; databases are reached only through the Data API
  • The ALB accepts CloudFront traffic only, behind WAF; no public S3
6

Least-privilege IAM

  • Separate roles: harvest (read-only metadata), assistant (metadata store + Bedrock), jobs
  • No wildcard actions; scoped database roles
  • Infrastructure as code only (CDK); everything tagged
Automated security self-check: ✔ 7 pilot controls pass Budget alerts + automatic deny No public S3; KMS encryption on all buckets No wildcard IAM on pilot roles Aurora & Redshift private, encrypted CloudTrail + Bedrock invocation logging Redshift RPU usage limit PHI guard: no row values in store / prompts / logs ⚑ IAM-user keys > 30 days (account-level, outside pilot)

Evaluation techniques

  • Ground-truth golden set: questions generated from the planted defects, the true lineage and the data model, across 7 categories
  • Tool-trajectory scoring: did the agent call the expected tools?
  • LLM-as-judge + rubric: per-question rubric facts and a JSON verdict
  • Citation precision and recall: cited asset keys are checked against tool results (hallucination check)
  • Adversarial tests: write requests, restricted data and prompt attacks must be refused or hidden (100% target)
  • Latency p50/p95, run in AWS with the production code, roles and models (make eval)

How we improved the agent

Correctness 74% → 92%   Tool calls 93% → 99%
  • Error analysis of each failed question, by category, after every eval round
  • Prompt engineering: tool-routing rules (DQ questions call get_dq_issues first), impact ranking, cite-only-what-tools-return
  • Tool hardening: fuzzy asset-key resolution, vocabulary normalisation (issue types, segments, domains), DQ fallbacks
  • Deterministic checks where the LLM is weak: doc-lint for outdated documentation
  • Defence in depth: entitlements are enforced inside tools, not by the prompt; Guardrail plus a write-intent check
  • Model-agnostic harness: switch to GPT-5.6 in config and re-run to compare

Sample prompts & real responses (1/2)

demo-analyst
“Why did Louisiana claims volume drop yesterday?”
Tools: search_assets, get_dq_issues · 6.94 s · ✔ correct

What happened?

  • The redshift://eqh/core/claim_header table shows a high‑severity volume anomaly for Louisiana (segment state=LA).
  • Yesterday’s count was 111 rows, a ‑65.9 % change versus the 7‑day baseline average of ~326 rows (z‑score ‑9.04).

Why the drop?

  • The anomaly flag is raised when the inbound claim feed (the raw Medicaid claim extracts that populate claim_header) delivers far fewer records than expected.
  • This usually points to an upstream issue such as:
  • Delayed or missing file delivery from the state Medicaid clearinghouse,
  • Parsing error on the daily extract (e.g., a schema change that caused the loader to reject rows), or
  • Source‑system outage on the LA Medicaid provider portal.

Business impact

  • The downstream impact is labeled actuarial_datashare – actuarial models that rely on claim counts will see an artificial dip, potentially skewing risk‑adjusted payments and forecasts.

Which downstream objects depend on the HbA1c result value column?

Down‑stream category Asset (key) How it is used Why a type change matters
Payer submissions redshift://eqh/outbound/payer_supplemental_quality_file The view builds the “quality file” that is sent to each Medicaid payer; it pulls the numeric HbA1c value (via result_value) to compute the HBA1C‑control flag. If the column type changes (e.g., from NUMERIC to VARCHAR) the numeric‑only calculations will fail or produce wrong flags, breaking the file that payers expect.
CareEmpower feeds redshift://eqh/vbc_mart/v_member_lab_measures This curated VBC mart view supplies member‑level lab measures to the CareEmpower analytics platform (including the HBA1C control indicator). The view references the same column (as result_numeric and the derived flag gsd_hba1c_controlled). A type change can cause the view compile error or silently return nulls, breaking the CareEmpower feed.
