Challenges from the customer brief

Discovery

Hard to find the right dataset for a metric (e.g. "ED per 1,000 for AZ Medicaid").

Documentation

Inconsistent, terse or outdated comments; cryptic finance views.

Impact

Downstream consumers (payer files, CareEmpower, datashares) are hard to see.

Manual DQ

Missing, duplicate, stale, drifted and RI issues found late and by hand.

Key-person risk

Dependence on a few experienced engineers; slow onboarding.

Multi-payer quirks

Each payer's feed format, cadence and failure modes differ by state.

Silent breakage

Late-binding views keep compiling while upstream types change.

Sensitive data

SDoH / behavioral-health data must be entitlement-filtered.
At risk: payer quality submissions, outbound practice deliveries, VBC analytics (PMPM, ED/1000, shared savings) and every future AI use case that depends on trusted data.

Target agent, architecture & evaluation

A thin, governed layer beside the lake, Redshift, Glue Catalog, BI and datashares — it never replaces them, and it never changes data.

The target: a governed, read-only data assistant

Answers

Sample prompt · B7-01

demo-analyst · groups analyst
“Where do I find ED visits per 1,000 by practice for Arizona Medicaid?”
Tools: search_assets
Latency: 6.74 s · ✔ judged correct
Discovery: picks the curated mart and explains the AZ / Medicaid filters.

Where to find the metric

  • Dataset: redshift://eqh/vbc_mart/ed_visits_per_1000_by_practice – a view that provides ED visits per 1,000 member‑months (or member‑years) broken out by practice and month.
  • This view is built on the core claims tables and already contains the state dimension, so you can filter to Arizona Medicaid in your query (e.g., where state = 'AZ' and payer_type = 'MEDICAID').

How to use it

  1. Connect to the Redshift cluster eqh.
  2. Query the view, adding the state and payer filters you need, for example:

sql select practice_id, month, ed_visits_per_1000 from redshift://eqh/vbc_mart/ed_visits_per_1000_by_practice where state = 'AZ' and payer_type = 'MEDICAID';

  1. The result gives you the ED visit rate per 1,000 members for each practice in Arizona Medicaid for each month.

If you need a aggregated annual figure, wrap the query in a SUM/AVG over the desired months. This view is the most downstream, ready‑to‑use source for the metric you asked about.

Sample prompt · B7-03

demo-analyst · groups analyst
“Explain `vbc_mart.practice_shared_savings_calc` in plain language.”
Tools: get_asset, search_assets
Latency: 6.81 s · ✔ judged correct
Explanation of an undocumented finance view (D09) — decodes cryptic columns from lineage.

vbc_mart.practice_shared_savings_calc – plain‑language overview

  • What it is: A Redshift view that pulls together every piece of data needed to calculate how much “shared‑savings” each medical practice earned for a given performance year.

  • Key inputs it combines

  • Benchmark PMPM – the cost per member‑per‑month that the payer expects (the “target”).
  • Actual PMPM – the real cost the practice achieved for its members.
  • Gross savings – the dollar difference between benchmark and actual (if actual is lower, it’s a saving).
  • Practice‑level contract terms – share‑percentage, contract type, and any quality thresholds that must be met before savings can be paid.
  • Member‑month counts – the number of member‑months the practice served, used to scale the PMPM figures to total dollars.

  • Net savings – the portion of gross savings that the practice actually receives after applying the contract share and any quality adjustments.

  • What it produces

  • One row per practice × performance year that includes:

    • Total member‑months covered
    • Benchmark and actual PMPM values
    • Gross and net savings amounts
    • Contract share % and type (e.g., “Full‑Risk”, “Partial‑Risk”)
    • Flags indicating if quality thresholds were met

  • Why it matters

  • Finance & Payer submissions: The net‑savings figure is fed into outbound payer settlement files and CareEmpower incentive feeds. Errors here would cause incorrect payments to practices or mismatched payer reports.
  • Practice performance reporting: Practices use these numbers to see how well they did against cost targets and to validate incentive statements.

  • Analytical marts: Down‑stream VBC marts (e.g., cost‑by‑practice or scorecards) rely on this view for any cost‑saving analyses.

  • Source lineage (high‑level)

  • Pulls raw benchmark/actual PMPM data from shared_savings_settlement tables (core & spectrum layers).
  • Joins contract details from the practice_contract table.
  • Uses member‑month counts derived from the claims mart (pmpm_cost_by_practice) and the practice roster (practice).

Which downstream objects use the HbA1c result‑value column (type‑changed) ?

Downstream category Affected assets (via the result_value column) Why it matters
Outbound payer submissions redshift://eqh/outbound/payer_supplemental_quality_file (via result_value → 2 hops)
 Extract: extract://payer_supplemental_quality_file (3 hops)		 The file sent to each state payer contains the numeric HbA1c result; a type change can break the file schema and cause rejections on the payer‑SFTP.
CareEmpower / internal marts redshift://eqh/vbc_mart/v_member_lab_measures (via result_numeric – 1 hop) This view powers the CareEmpower “Lab Measures” feed and many analytics dashboards; the view is late‑binding, so a type change can silently produce NULLs or conversion errors that downstream users won’t see until the feed is consumed.
Other consumers user://analyst_quality (direct read)
user://svc_extract_runner (3 hops)
target://PAYER_AZ1 SFTP (4 hops)		 Analyst notebooks, extract‑run services and the final payer‑AZ1 SFTP target all depend on the outbound file; they will inherit any schema breakage.

Key points

  • The column is late‑binding in the view v_member_lab_measures, meaning the view recompiles after the upstream type change. Errors can appear only when the view is materialised for the outbound file, so they may be missed in routine checks.
  • The highest‑impact breakage is the payer supplemental quality file – if the column type no longer matches the file definition, the payer will reject the submission, halting quality‑measure reporting.
  • CareEmpower dashboards that show HbA1c control rates will also show incorrect or missing values, affecting clinicians and quality‑improvement teams.

Why the Louisiana claim‑line volume fell yesterday

Metric (segment) Yesterday’s rows % change vs. 7‑day baseline
claim_line (payer_code = PAYER_LA1) 338 ‑66 % (z‑score = ‑7.23)

The platform’s data‑quality engine flagged a high‑severity “volume_anomaly” on the core claim‑line table for the Louisiana payer (see issue on redshift://eqh/core/claim_line). The drop is not a business‑trend but an ingestion failure.

What caused it
