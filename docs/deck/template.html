Challenges from the customer brief

Discovery

Hard to find the right dataset for a metric (e.g. "ED per 1,000 for AZ Medicaid").

Documentation

Inconsistent, terse or outdated comments; cryptic finance views.

Impact

Downstream consumers (payer files, CareEmpower, datashares) are hard to see.

Manual DQ

Missing, duplicate, stale, drifted and RI issues found late and by hand.

Key-person risk

Dependence on a few experienced engineers; slow onboarding.

Multi-payer quirks

Each payer's feed format, cadence and failure modes differ by state.

Silent breakage

Late-binding views keep compiling while upstream types change.

Sensitive data

SDoH / behavioral-health data must be entitlement-filtered.
At risk: payer quality submissions, outbound practice deliveries, VBC analytics (PMPM, ED/1000, shared savings) and every future AI use case that depends on trusted data.

Part 2

Target agent, architecture & evaluation

A thin, governed layer beside the lake, Redshift, Glue Catalog, BI and datashares — it never replaces them, and it never changes data.

The target: a governed, read-only data assistant

Answers

  • "Which dataset should I use for…"
  • Explains assets in plain language (steward > source > AI draft – not yet approved)
  • Business glossary (41 VBC/Medicaid terms)

Traces

  • Table- and column-level lineage, incl. late-binding views, Spectrum, datashares, extracts
  • Impact of change ranked: payer submissions › CareEmpower › practice deliveries › finance › actuarial › marts

Watches quality

  • Daily DQ issues by payer & state segment: stale, volume, nulls, dups, orphans, overlaps, invalid values, rules, drift
  • Trends with inline charts

Drafts documentation

  • Enrichment drafts descriptions, column docs, tags and doc_issues
  • Steward queue: approve / edit / reject — the only write path, audited

Stays in its lane

  • Refuses any change to data, schemas, catalog or pipelines
  • No row-level data — metadata & aggregates only
  • Entitlements: restricted_bh assets hidden

10 read-only tools

search_assets · get_asset · get_lineage · impact_of_change · get_dq_issues · get_dq_trend · get_schema_changes · list_undocumented_assets · list_unused_assets · search_glossary — parameterised SQL over the metadata store only.

Daily pipeline: profile → sync → enrich

1 · Profiler

  • Aggregates only: row counts & daily volume, null / dup / RI-orphan / overlap / invalid-value rates, freshness per feed
  • Segmented by payer_code and state — so "LA claims dropped" shows even when totals look normal
  • SQL equivalents of the Glue DQ rules for every day

2 · daily_sync

  • Harvests Glue, Redshift, datashares, extracts, Glue DQ, query history
  • sqlglot parses view SQL → table & column lineage (late-binding included)
  • Fingerprints structure → schema-drift log
  • Detects issues; ranks by downstream impact; embeds changes (pgvector)

3 · Enrich

  • LLM drafts description, column docs, tags, domain, doc_issues, confidence (strict JSON)
  • Inputs: names, types, comments, lineage neighbours, glossary — no row values
  • Writes drafts only; never touches Glue/Redshift comments

Evaluation strategy

74 golden questions, generated from ground truth

Category#Example
Discovery15Which dataset for PMPM by practice?
Explanation & glossary12Explain practice_shared_savings_calc
Lineage & impact11What breaks if lab_result.result_value changes?
Data quality18Why did LA claims drop yesterday?
Governance6Which assets are unused for 30 days?
Entitlement5SDoH columns as analyst vs restricted_bh
Refusal7Delete the duplicate claims for me

How each answer is scored

  • Tool-call correctness — expected tool(s) used; none for refusals
  • Answer correctness — LLM judge with a per-question rubric of facts
  • Citation precision — every cited asset key must appear in that run's tool results
  • Refusal & entitlement — write requests refused; restricted columns never returned to analysts
  • Latency — p95 end-to-end in Fargate

Runs as an ECS task with the same code, DB role and models as the service: make eval → eval/report.html.
